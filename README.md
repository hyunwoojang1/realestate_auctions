# 부동산 경매 차익 큐레이션 (auction-arbitrage)

> **법원경매에 나온 아파트·오피스텔을 "실거래 시세 대비 얼마나 싼가(차익)"로 자동 랭킹하는 사이트.**
> 한 줄로: *"실거래와 최저입찰가의 괴리를 보여주되, 그 시세를 어디까지 믿어도 되는지 함께 말해주는 1차 필터."*

**프로덕션:** https://auction-arbitrage-nine.vercel.app

법원경매 물건의 **최저입찰가**를 **국토부 실거래 가격밴드**(검증 하한가~기준가)와 매칭하고, 취득세 등 객관
비용을 차감한 **보수 기준 차익**을 계산해 후보를 걸러줍니다. 핵심 가치는 높은 수익률 표시가 아니라
**"이 데이터를 어디까지 믿어도 되는지"** 를 모든 수치에 병기하는 것입니다(비교군 출처·표본 수·신뢰 게이트).

이 프로젝트에서 **가장 중요한 엔진은 크롤링 계층**입니다 — 여러 원천(대법원 법원경매·국토부 실거래·
네이버·건축물대장)을 각기 다른 프로토콜·차단정책으로, **차단당하지 않고 정중하게** 수집해야 나머지
매칭·스코어가 성립하기 때문입니다. 이 README는 그 크롤링 로직을 미래의 유지보수자(사람이든 AI든)가
코드를 열기 전에 전체 그림을 갖도록 아주 자세히 설명합니다. 모든 수치는 실제 코드 값입니다.

# 크롤링 엔진 상세

> 이 프로젝트의 심장. **원천(대법원·국토부·건축HUB)에서만** 수집하고 유료 경매사이트의 가공 데이터는
> 크롤링하지 않습니다. IP 로테이션·프록시는 **명시적으로 거부**(합법·정중 전제와 정면충돌) — 단일 IP
> 정중 크롤이 상한입니다.

## 크롤러 지도 — 누가, 무엇을, 어떤 정책으로

| 크롤러 | 진입점 | 원천/프로토콜 | 병렬 정책 | 요청 예산 |
|---|---|---|---|---|
| 목록(물건 검색) | `run.py --source courtauction` | 대법원 POST JSON | **순차 전용** | 동적 산출(비영속, 아래) |
| 상세·권리·사진 | `python -m deploy.crawl_rights` | 대법원 POST JSON | **순차 전용** | 500/일 **파일 영속** |
| 현황조사서(임차인) | crawl_rights + `AUCTION_CRAWL_TENANTS=1` | 대법원 POST JSON | 〃 (물건당 +1콜) | 위와 공유 |
| 실거래 시세 | `run.py --live` → `pipeline.load_live_trades` | 국토부 공공 XML API | **병렬 12워커** | 무료키 쿼터(캐시로 절약) |
| 네이버 시세·실거래 | `python -m deploy.crawl_naver` | Playwright in-page fetch | **순차 전용** | 없음(지터+세션갱신) |
| 건축물대장 | `python -m deploy.enrich_building` | 건축HUB·VWorld XML/JSON | 병렬 4워커 | 무료키 쿼터(dedup 절약) |

핵심 원칙: **"어디를 긁느냐에 따라 다른 정책"**. 대법원·네이버는 안티봇이 있어 순차+지터+즉시중단,
국토부·건축HUB는 승인된 공공 API라 병렬 허용(단 429 백오프·쿼터 절약은 함).

## 공통 설계 — 밴(차단) 회피 철학

| 원칙 | 구현 |
|---|---|
| **순차 전용(병렬 금지)** | courtauction·naver는 concurrency=1. 한 IP에서 동시요청은 즉시 봇 신호. |
| **랜덤 지터 지연** | 고정간격이 아니라 매번 난수 지연(courtauction 3~8초, naver 실운용 1.0~2.2초). 고정간격=봇. |
| **일일 총량 상한** | courtauction 500/일 서킷브레이커. **재시도 포함 '실제 발신 요청 수'** 기준(=WAF가 보는 트래픽). |
| **예산 파일 영속(D1)** | `.courtauction_budget.json`에 `{date, count}`를 **매 요청마다** 기록 — 프로세스 재시작·병렬 실행에도 당일 누적을 이어받음. 종전 인스턴스 리셋으로 하루 6,119콜(상한 12배) 실측 사고의 재발 방지. |
| **지수 백오프** | 429/5xx는 `2→4→8…`초(+지터). `Retry-After` 헤더가 오면 그 값(최소 60초) 존중. |
| **차단 시 우회 금지** | 403·3xx 리다이렉트 감지 시 **즉시 전체 중단**(`CourtAuctionBlocked`/`NaverBlocked`). 헤더 바꿔 뚫지 않음. |
| **조용한 차단(silent block) 감지** | 200인데 비-JSON/스키마 붕괴/HTML 챌린지면 "위장 차단"으로 보고 중단 — '데이터 없음'과 구분. |
| **kill-switch 파일** | `COURTAUCTION_STOP` / `NAVER_STOP` / `PHOTO_MIGRATE_STOP` 파일이 존재하면 다음 요청 전 즉시 종료. 밤샘 루프의 `AGENT_STOP`과 의도적으로 분리. |
| **개인정보 미저장** | 파서 단계에서 성명 등 PII를 제거·마스킹하고 **불리언·금액·유형만** 남김(아래 PII 섹션). |
| **부분 성공 보존** | 차단으로 중단돼도 그때까지 수집분은 저장하고, 다음 실행이 이어받음(resume). |

## ① 대법원 법원경매 (courtauction) — 가장 중요한 크롤러

`src/courtauction_client.py`(요청·안전장치) · `src/courtauction_fields.py`(목록 파싱·PII)
· `src/courtauction_detail.py`(상세 파싱) · `src/courtauction_rights.py`(권리 텍스트 검출기)
· `deploy/crawl_rights.py`(상세 배치 크롤)

### 엔드포인트 4종 (실측 리버스 엔지니어링 — 공개 API 문서 없음)

```
GET  /pgj/index.on                              세션 쿠키 발급(워밍)
POST /pgj/pgjsearch/searchControllerMain.on     물건 목록 검색
POST /pgj/pgj15B/selectAuctnCsSrchRslt.on       물건 상세(권리요지·기일·청구금액·사진)  pgmId=PGJ151F01
POST /pgj/pgj15B/selectCurstExmndc.on           현황조사서(임차인 전입일·보증금)         auctnInfOriginDvsCd="2"
```
`www.courtauction.go.kr`는 화면만 있어 Playwright로 실제 브라우저의 XHR을 캡처해 역설계했습니다.
새 엔드포인트가 필요하면 **추측 파서 금지** — `deploy/probe_detail.py`처럼 라이브 1콜 정찰로 응답을
확정한 뒤 파서를 씁니다.

- **검색 페이로드**: `{"dma_pageInfo": {...}, "dma_srchGdsDtlSrchInfo": {...}}`. 서버가 빈 값도 요구해
  `SearchFilter._ALL_KEYS` 41개 키를 전부 `""`로 깔고 설정값만 덮어씁니다. 부동산 고정값
  `cortAuctnSrchCondCd="0004601"`.
- **상세 페이로드**: `{"dma_srchGdsDtlSrch": {"csNo", "cortOfcCd", "dspslGdsSeq", "pgmId": "PGJ151F01"}}`.
  `csNo`는 "2025타경669" 사용자 포맷 그대로 수용(실측).
- **현황조사서 전제조건(중요)**: **같은 세션에서 같은 사건의 상세(case_detail)를 먼저 호출**해야 응답이
  옵니다. 선행 없으면 HTTP 200 + `{ipcheck:false}` 빈 응답(소프트 차단과 동일한 모양).
- **위장 헤더**: requests 기본 UA는 즉시 차단(실측). Chrome/126 UA + `Referer`/`Origin`/
  `X-Requested-With: XMLHttpRequest`/`Content-Type: application/json;charset=UTF-8` 필수.
- **세션 쿠키**: `wcCookieV2`에 **클라이언트 IP가 박혀** 있어 가정용 동적 IP가 도중에 바뀌면 무효화
  → 403/리다이렉트로 드러나고 회로차단기가 중단(자동 재워밍은 의도적 미구현).

### 안전장치 수치표 (`CourtAuctionClient` 기본값)

| 항목 | 값 |
|---|---|
| 요청 간 지터 | `random.uniform(3.0, 8.0)`초 (crawl_rights `--min-interval/--max-interval`로 조절) |
| 일일 상한 | `daily_cap=500` (crawl_rights `--cap`으로 오버라이드) |
| 예산 영속 파일 | `.courtauction_budget.json` — `{"date":"YYYY-MM-DD","count":N}`, 매 요청마다 저장 |
| 재시도 | 4회 (네트워크 오류·429·5xx만), 백오프 `min(120, 2×2^(n-1)) + U(0,2)`초 |
| Retry-After | 헤더 존중, 최소 60초 |
| 타임아웃 | 30초 |
| 페이지 크기 | 40행 고정(200 요청 시 HTTP 400 — 실측 상한) |
| kill-switch | `COURTAUCTION_STOP` 파일, 매 요청 전 검사 |
| 카나리 | 서울(`sido_cd="11"`) 1페이지 사전 조회 — 0건이면 조용한 차단 의심으로 시작 안 함 |

**silent-block 판정**: 200이어도 ①Content-Type 비-JSON ②JSON 파싱 불가 ③`data`/`dlt_srchResult`/
`dma_pageInfo` 없음(목록) ④`dma_result` 없음(상세) → 전부 `CourtAuctionBlocked`. 단 **현황조사서만
관대 검증**(JSON이기만 하면 통과) — 임차인 없는 물건의 빈 리스트가 정상이기 때문.

**예외 계층**: `CourtAuctionError`(일반 실패 — 물건 단위 스킵 가능) ⊂ `CourtAuctionBlocked`
(차단·상한·킬스위치 — **즉시 전체 중단** 신호).

**⚠ 예산 영속의 실제 배선(주석과 코드가 갈리는 지점)**: `budget_file`을 실제로 켜는 곳은
`deploy/crawl_rights.py`뿐입니다. 목록 크롤(`pipeline.load_courtauction_nationwide`)은 아래 동적 예산을
`daily_cap`으로 주입하지만 **비영속**(프로세스 재시작 시 리셋)입니다.

### 목록 검색 (`search` / `affordable_search`)

- **서버에서 실제 작동하는 필터만** 사용(실측): 지역·감정가·최저가율·면적·유찰횟수·용도.
  **절대 최저가 필터는 서버가 무시**하므로 2단 전략 — 서버에는 `감정가 상한 = 현금 × 3.0`
  (`--appraisal-buffer`, 다회유찰 저가매물 누락 방지)으로 볼륨만 줄이고, `0 < 최저가 ≤ 현금` 정밀
  필터는 **로컬에서** 겁니다.
- **페이지네이션**: 1페이지 `totalYn="Y"`로 총건수 확보 → `min(max_pages, ceil(total/40))`까지.
  totalCnt 도달 시 조기 종료(불필요 요청 0).
- **누락을 침묵하지 않음**: `max_pages`에 잘리면 WARNING("검색 잘림 — --max-pages 상향 필요"),
  잔여가 있는데 빈 페이지면 ERROR(서버 이상/조용한 차단 의심), 수집률 <90%면 WARNING.
  (부산 등 대형 시도 매물 수백 건이 매일 조용히 빠지던 감사 발견의 재발 방지.)
- 행마다 `parse_row` → `sanitize_row`(PII 제거) → `CourtAuctionRecord`. **min_bid_price는
  `notifyMinmaePrice1`(공고가) 우선** — `minmaePrice`는 '직전 회차' 가격이라 73.6% 물건에서 다름(실측).
- **물건유형 3단 분류**: ①세부용도코드 `sclsUtilCd` 정확매핑(20104=아파트, 20110=오피스텔 등)
  ②그룹명 키워드 폴백(복수 그룹+코드 미상이면 "혼합"=시세추정 미지원) ③물리 교차검증 — 주거유형인데
  건물 표식이 전무하고 지목만 있으면 **"토지"로 교정**(나대지가 용도명 '아파트'로 와서 4.45억 허상
  차익이 노출됐던 실사고).
- **목적물 다중 행 병합**(`merge_mokmul_rows`): 일괄매각 물건이 목적물(mokmulSer) 단위로 여러 행으로
  옴 → 건물 표식 있는 행 우선 병합(마지막 행 승리로 아파트가 '토지'로 강등되던 순서 의존 버그 수정).

### 전국 샤딩 수집 (`pipeline.load_courtauction_nationwide`)

- 17개 **시도**(법원 아님) 코드를 **하나의 client로 순차 샤딩** — 일일상한·지터·세션이 시도 전체에
  누적 적용. "1→700 한 번에 훑는" 봇 패턴 대신 시도별 구간 분할. 워밍은 첫 시도에서만.
- **동적 요청예산**: `budget = max(500, 시도수 × (max_pages + 2) + 100)` → `daily_cap`으로 주입.
  (+2=워밍업, +100=재시도 여유. 고정 500이 페이지 캡보다 먼저 끊어 데이터 의존적 부분수집이 나던
  감사 CRITICAL의 수정.)
- **부분수집 신호**: 도중 차단되면 부분결과 반환 + `pipeline.NATIONWIDE_PARTIAL=True` → run.py가
  전량교체(replace_all)를 **병합(upsert)으로 강등**하고 캐시 덮어쓰기를 스킵합니다. 부분 스냅샷으로
  전량교체하면 미수집 시도의 물건·권리가 로컬·클라우드에서 삭제되기 때문(감사 CRITICAL).

  case_no 단독 키는 금물(전 계층 공통 규칙 — 캐시·좌표·권리 조인 모두 court 포함).
- CLI 기본 `--max-pages 25`(주의: 파이프라인 함수 기본값은 10 — 직접 호출 시 다름), 일일 새로고침은
  `-MaxPages 120`(현금 10억 확장으로 대형 시도 113페이지 실측 → 전수. totalCnt 조기종료라 실요청은
  필요분만).

### 물건 상세·권리 크롤 (`deploy/crawl_rights.py`) — 물건당 API 1콜

목록 검색엔 **권리·임차·점유 정보가 없습니다**(pgj15B 응답에 임차인 표가 아예 없음도 라이브 정찰로
확정). 상세 크롤이 매각물건명세서 요지(인수권리 `ndstrcRghCtt`/최선순위 `tprtyRnkHypthcStngDts`/
유치권 등 `sprfcExstcDts`)·기일 역사·청구금액·배당요구종기·감정 요항·현장사진을 가져옵니다.

**backlog(미수집 물건) 관리** — 영속 테이블이 아니라 매 실행 시 SQL로 도출하는 resume 구조:
```
targets = scored_listings ⋈ raw_listings (court, case_no, item_no 복합키 조인)
        − listing_rights 기존 키(--refresh 없으면)
        + raw 다-docid 팬아웃 중복제거(D2 — 미제거 시 같은 사건에 최대 52배 요청 실측)
        → 우선순위: 보수차익 양수 큰 순 → 유찰 많은 순 → [:limit]
```

**물건별 처리 루프의 방어선**:
1. `CourtAuctionBlocked` → 즉시 전체 중단(exit 2). `CourtAuctionError`·기타 예외(ConnectionReset 등)
   → 해당 물건만 스킵하고 계속(크래시<미탐<완주).
2. **(C6) 응답 사건번호 대조**: 응답 `userCsNo`와 요청 사건번호를 canonical("YYYY타경NNNN") 환원 후
   비교 — 확실히 다를 때만 스킵(오사건 권리 영구 적재 차단. 표기차로 전량 오거부되던 것을 canonical
   비교로 견고화).
3. **(H4) 스키마 드리프트 카나리**: 핵심 3키(`ndstrcRghCtt`/`tprtyRnkHypthcStngDts`/`sprfcExstcDts`)의
   **키 이름 존재**를 검사(값 null은 정상 — 매각기일 1주 전 미공개 명세서가 그 모양). **셋 전부**
   있어야 정상 — 종전 `any()` 판정은 최고위험 필드 하나만 개명돼도 무경보(QA CRITICAL)라 수정.
   드리프트여도 저장은 하되 집계해 게이트로.
4. `normalize()` 후 `is_empty`(요지 전부 빈 값)면 **저장 안 함** — 빈 명세서를 저장하면 '권리 깨끗'
   오판(거짓 안전 신호).
5. **10건마다 중간 저장** + finally에서 잔여 배치 저장(마지막 실패 시 최대 9건 유실 방지).
6. 종료 후 data_gates 전 배치 PASS 시에만 Supabase 미러(`upsert_rights`/`upsert_photos`).

**exit code 계약** (스케줄러가 부분 중단을 성공과 구분하는 침묵실패 방어):

| exit | 의미 | 운영 대응 |
|---|---|---|
| 0 | 정상 | — |
| 1 | data_gates FAIL — 로컬 저장은 유지, 클라우드 미러만 차단 | validate_data로 위반 확인 |
| 2 | 차단/일일상한 도달 중단(수집분은 저장됨) | 밴 의심 — 다음 사이클 `-SkipRights` 권장 |
| 3 | 실패율 >50% 또는 (processed≥20에서) 드리프트율 >30% | 법원 스키마 변경 의심 — 파서 점검 |

CLI: `--limit`(기본 200) `--all` `--refresh` `--estimable`(사진 대상만, 이어받기) `--force` `--no-cloud`
`--cap` `--min-interval` `--max-interval`.

결정적 차이. 밴 회피가 아니라 **쿼터 절약**이 설계 목표입니다.

### 엔드포인트 6종 (GET, XML 응답)

```
apt        RTMSDataSvcAptTradeDev   (건물명 태그 aptNm)
rh         RTMSDataSvcRHTrade       (연립다세대, mhouseNm)
officetel  RTMSDataSvcOffiTrade     (offiNm)

params: serviceKey, LAWD_CD(법정동 5자리), DEAL_YMD(YYYYMM), pageNo, numOfRows(1000)
```
거래금액은 `'34,500'`(만원+콤마) → 콤마 제거 후 ×10,000 원 환산.

### 수집 로직의 핵심 디테일

- **스코프 절약**: 시세추정 지원 유형(아파트·오피스텔)이 실재하는 법정동만 호출 — 토지·상가만 있는
  지역까지 긁으면 시세에 안 쓰이면서 쿼터만 태워 429.
- **다개월 창**: `recent_ymds(기준월, live_months)` — config 기본 12개월, 일일 새로고침은 24개월.
- **열린 달 / 닫힌 달 이원 캐시**(molit_cache, SQLite `data/molit_trades.db`, PK=(kind,lawd_cd,ymd)):
  이번 달+직전 달(열린 달)은 지연 신고 반영 위해 **매번 재수집**(캐시 안 함), 그 이전(닫힌 달)은
  **한 번 받으면 영구 보관**(시간 TTL 없음 — "TTL"이 아니라 이원 정책). 빈 달(`[]`)도 캐시해 재fetch
  차단. 쿼터 중간 소진 시 받은 만큼 캐시돼 다음 실행이 이어받음. 소급 정정은 캐시 퍼지+재수집 또는
  `scripts/reprocess_real_trades.py`.
- **병렬 fetch**: ThreadPool 기본 **12워커**(`AUCTION_MOLIT_WORKERS`). 닫힌 달 캐시는 메인스레드에서
  선조회, 워커는 받기만 하고 **SQLite 쓰기는 메인스레드만**(락 회피). 개별 실패는 집계 후 계속 진행
  — 실패가 있으면 "시세추정불가가 comps 부재가 아니라 API 실패 때문일 수 있음" 경고(침묵실패 구분).
- **지역 태깅(중요)**: 각 거래에 호출 시점 `LAWD_CD`를 박음 — 없으면 전국 풀에서 타지역 동명(서울
  신정동 ↔ 대구 신정동)이 comps로 혼입돼 시세 왜곡.
- **해제거래 제외**: `cdealType="O"`(실측값 — 'Y' 아님!) 또는 `cdealDay` 존재 시 `is_cancelled` —
  파싱은 보존하고 매칭에서 제외(안 걸러내면 시세 +11.18% 부풀림 실측).
- **마지막 페이지 판정**: 필터 후 건수가 아니라 **원본 행 수(raw_count)** 기준 — amount≤0으로 걸러진
  행 때문에 조기 종료돼 comps가 누락되는 편향 방지.
- 재시도 3회: 일반 백오프 `2^(n-1)`초, **429는 Retry-After 존중(없으면 3×2^(n-1)초) + U(0,1.5) 지터**
  (병렬 워커 동시 재폭주 방지). 소진 시 `MolitApiError`. 스로틀: 라이브 fetch 후 0.25초
  (`AUCTION_MOLIT_THROTTLE`).

### molit_bridge — 네이버 확정쌍의 최신 거래 보충

네이버 실거래는 순차 크롤이라 신선도가 느림 → 네이버 확정쌍(complexNo)의 과거 이력 **(월, 가격, 층)
정확일치 지문**으로 국토부 aptNm 그룹을 이름 퍼지매칭 없이 확정하고, "네이버가 아직 못 본 최신
거래"만 메모리 보충(DB에 안 씀, 채점 1회용). 보수 게이트: 지문 ≥3건, 커버리지 ≥0.6, 1위 ≥ 2위×2,
보충 ≤20건/물건, **열린 달(최신 2개월)만 주입**(닫힌 달은 영구 캐시라 뒤늦은 해제신고 미반영 위험).
그룹키에 동(洞) 포함(압구정 현대 vs 삼성동 현대 병합 차단). `AUCTION_MOLIT_BRIDGE=0`으로 비활성.

### 키·오류 안전

- `serviceKey`는 로그·예외에서 정규식 마스킹(`serviceKey=***`) — requests가 URL에 키를 싣기 때문.
- HTTP 200이어도 본문이 OpenAPI fault(`returnAuthMsg`)거나 `resultCode ∉ {"00","000"}`이면
  `MolitApiError` — 조용히 빈 결과로 두지 않음.

## ③ 네이버 부동산 (KB시세·호가·실거래) — 시세 폴백 + 확정 comps

`src/naver_client.py`(Playwright) · `src/naver_store.py`(SQLite 5테이블) · `src/naver_match.py`(단지 매칭)
· `deploy/crawl_naver.py`(배치)

국토부 이름매칭이 약한 물건에 **complexNo 확정 실거래**를 붙이는 새 1차 경로 + KB시세/호가 폴백.

### 왜 Playwright인가

네이버는 토큰/쿠키 없는 순수 요청을 429로 거부합니다. 그래서:
1. Playwright(chromium, headless)로 실제 지도 페이지(`new.land.naver.com/complexes?...`)를 띄우고,
2. 페이지가 자기 API를 호출할 때 request 인터셉트로 `authorization` 토큰을 캡처(최초 1회),
3. **페이지 컨텍스트 안에서 `fetch()`** 실행(쿠키·토큰 자동 동봉). 토큰 대기: 500ms×20회(최대 10초),
   실패 시 `NaverBlocked`.

### 엔드포인트 카탈로그 (전부 in-page GET)

```
/api/cortars                          좌표 → 법정동코드(cortarNo)
/api/regions/complexes                법정동 → 단지 목록 (realEstateType=APT/OPST — 오피스텔 분기 필수!)
/api/complexes/{cno}                  단지 상세(평형목록)
/api/complexes/overview/{cno}         세대수·매물수·전세가율·사용승인일
/api/complexes/{cno}/prices?provider=kbstar          KB시세 시계열
/api/complexes/{cno}/prices/real      실거래(커서 페이지네이션: addedRowCount 누적)
/api/articles/complex/{cno}           현재 매물 호가(20건/페이지, isMoreData 종료, 상한 5p)
```

**⚠ 단위 함정(실측 사고)**: 네이버 API는 **만원 단위**. 호가 API `priceMax=999999`(=99.9억)가 정답 —
원 단위 `99900000000`을 넣으면 서버가 **200 + error 바디**로 거부해 호가 수집이 통째로 침묵 사망했던
이력. 200+error 바디는 경고 로그 후 빈 결과(침묵 0건 금지). DB 저장은 원 단위(×10,000).

### 안전장치

| 항목 | 값 |
|---|---|
| 요청 간 지터 | 실운용 `U(1.0, 2.2)`초(env `AUCTION_NAVER_MIN/MAX` — 4,899콜 무차단 실측 후 완화. 클래스 기본은 2.0~4.0초) |

| 429 백오프 | `30×(attempt+1) + U(0,15)`초 = 30~45 → 60~75 → 90~105초, 2회차에 세션 갱신 동반, 3회 소진 시 `NaverBlocked` |
| silent-block | 200인데 JSON 아님(챌린지 HTML) → 즉시 `NaverBlocked`. 403 등도 즉시. **404만** 정상 '없음' |
| 드라이버 크래시 | 에러 메시지에 driver/connection closed류 → playwright 통째 재시작(`_hard_restart` — 절전으로 드라이버 죽으면 브라우저 재생성만으론 무한대기, 실측) |
| kill-switch | `NAVER_STOP` 파일 — 매 fetch 전 검사, 부분 저장 유지 |
| 일일 예산 | **없음**(인스턴스 카운터뿐, 영속화 없음 — courtauction과 다름) |

`NaverBlocked`로 중단돼도 **exit 0**(부분 성공 = 정상 종료, 다음 실행이 이어받음).

### 배치 크롤 2단계 (`deploy/crawl_naver.py`)

- **Phase A(물건 단위 매칭)**: 대상 = 아파트·오피스텔 & 단지명 있는 scored 물건, **우선순위 큐** —
  ①시세 없는 물건(네이버가 유일한 희망) ②same_dong_fallback(오염 의심) ③나머지. 흐름: 좌표
  (coords 캐시) → cortar(좌표 0.001° 반올림 dedupe) → 단지목록 → 이름매칭 → 상세 → 평형 확증 →
  overview → KB시세 → 호가 전 페이지. 결과 status(`matched_kb/matched_ask/no_kb/no_match/no_coord`)를
  실패까지 저장해 이어받기 키로 사용(`--retry-failed`로 실패분만 재시도).
- **Phase B(`--backfill-real`, 쌍 단위)**: 매칭된 (complexNo, areaNo) 쌍의 실거래 백필.
  `naver_pair_status`에 **실거래 0건 쌍도 '확인함' 기록**해 재크롤 방지, `--incremental --stale-days
  14`로 오래된 쌍+신규만. 실거래 페이지 캡 env 기본 25p(80p는 쌍당 ~90콜·ETA 45시간 실측이라 축소,
  호가 제외로 쌍당 ~7콜). 쌍 단위 예외 격리 — `NaverBlocked`만 전체 중단.
- **영구 캐시 `data/naver_cache.json`**: 응답 **원본 통째 저장**(키 7종: cortar_pt, cortar_complexes,
  complex_detail, kb, arts, overview, real). 파싱 버그가 나도 재크롤 0으로 회수 —
  `scripts/reparse_naver_cache.py`(메타·KB·호가 재파싱), `scripts/reprocess_real_trades.py`(실거래
  재구축: 취소거래 판정값이 실제 `'O'`인데 `'Y'`를 찾아 취소 650건이 전부 시세 혼입됐던 C1 사고의
  소급 도구). 25건(A)/10쌍(B)마다 + finally 저장.

### 단지 매칭 (`naver_match.py`)

좌표로 법정동 먼저 특정(오매칭 방지) → RapidFuzz 이름 유사도 + **전용면적 확증**.

## 적재 안전장치 — 크롤 결과가 서빙을 오염시키지 않게

**전량교체(replace_all) 4중 안전장치** (run.py — 전량교체는 만료매물 제거용이지만 위험한 연산):

2. **커버리지 플로어(E1)**: 이번 수집이 기존 건수 × 0.8(`AUCTION_COVERAGE_FLOOR`) 미만이면 "만료가
   아니라 수집부실"로 병합 강등 — **차단 없이 수만 급감하는 silent-block**을 잡는 게이트.
3. **수집 0건 보존**: 교체·클라우드 미러 모두 스킵(빈 테이블은 data_gates를 위반 0건으로 통과해
   버리기 때문에 별도 장치가 필요).
4. 정상 교체 시에만 고아 정리 3종(rights/photos/naver — 고아 6,578·1,700행 실측 누적).

**품질 게이트 9종**(`data_gates.py`) — all PASS여야 Supabase 미러(로컬 적재는 유지): 유형-물리 정합
(토지 둔갑), 세부용도코드 정합, 시세/감정가 괴리(>2.5배), 조인 무결성, 지분 문구, 만료 매물, PK·가격
sanity, 권리 JSON 무결성, 밴드 순서. 게이트 자체의 버그도 FAIL로 기록(조용히 통과 금지). 도입 배경:
나대지가 아파트 실거래와 매칭돼 4.45억 허상 차익이 랭킹 상위 노출된 실사고.

샘플 fixture가 실매물인 척 서빙되던 감사 구멍 봉쇄.

# 권리 판정 엔진 상세 — 대항력 임차인·인수금액을 어떻게 판단하는가

> 차익 계산의 최대 함정은 시세가 아니라 **권리**입니다. 최저가가 아무리 싸도 대항력 임차인의 보증금을
> 떠안거나 유치권이 붙으면 차익은 허상이 됩니다. 이 엔진은 크롤한 법원 문서 **텍스트를 규칙(정규식+
> 키워드+날짜 비교)으로 판정**합니다 — LLM이 아니라 결정론적 규칙이므로, 모든 판정은 재현 가능하고
> 테스트로 고정돼 있습니다(`tests/test_courtauction_detail.py`, `test_rights_*`).
>
> **대원칙(보수 판정)**: 애매하면 위험 쪽(있음/인수/대항력)으로. 최악의 침묵실패는 "위험 물건을
> 깨끗하다고 표시"하는 false-negative이므로, 오탐(과잉 경고)과 미탐(누락) 중 항상 미탐을 더 무겁게
> 취급합니다. 단 "모름"과 "없음"은 엄격히 구분합니다(아래 §7).

(별도 크롤, 기본 OFF)에서만 얻습니다. 그래서 판정이 "문구 판정"(§1)과 "날짜 판정"(§2) 2계층입니다.

## §1. 전처리 — 판정 전에 텍스트를 어떻게 다듬나

판정 정확도의 절반은 전처리에서 나옵니다. 전부 실측 사고에서 역산된 규칙입니다.

1. **`_sanitize`**: HTML 엔티티 반복 해제(최대 3회 — `&amp;quot;` 이중 인코딩), 제어문자·제로폭·BOM
   제거, 공백 정규화. **마스킹·판정 전에** 적용 — 제로폭 문자가 이름/키워드 사이에 끼어 정규식이
   미스나던 실측 사고의 수정.
2. **`is_substantive` — "해당사항없음" 판정은 전체일치만**: 공백 제거 후 텍스트 **전체가**
   `없음/해당없음/해당사항없음`(+말미 구두점)일 때만 무해. `startswith` 판정은 "해당사항없음. 다만
   을구5번 임차권 인수" 같은 진짜 인수권리를 통째로 clean으로 삼켰던 실측 버그(#22).
3. **부정절 제거 `_strip_negated_clauses`**: 인수-해소 표현이 포함된 **절(clause)만** 삭제. 절 구분자는
   `[.\n;·,，]` — **콤마 포함이 핵심**(C4): "김철수는 인수하지 아니하고, 이영희는 매수인에게 인수됨"
   같은 다중임차인 한 문장에서 콤마가 없으면 부정절이 인수절까지 통째로 먹어 진짜 인수를 미탐.
   문서 전체를 버리지 않는 이유: "5번 임차권은 말소 동의, 7번 임차권은 인수" 혼재 시 인수 절은
   살아남아야 함.
4. **법정 서식 보일러플레이트 제거 2종**: ①대항력 쪽 — 모든 명세서에 인쇄되는 표준 경고문
   *"임차보증금은 매수인에게 인수되는 경우가 발생할 수 있고"* 는 존재 신호가 아님 → 제거 후 매칭.
   ②특수권리 쪽 — 표준 항목 안내문(*"등기된 부동산에 관한 권리 또는 가처분으로서 … 소멸되지
   아니하는 것"*, *"매각에 따라 설정된 것으로 보는 지상권의 개요"*)에 예시로 나오는 가처분/지상권을
   실제 권리로 오탐하면 **전 물건이 가처분 보유**로 오판(C1 실측) → 검출 전 삭제.

## §2. 대항력 임차인 — 1계층: 문구 판정 (`detect_tenant_opposable`)

명세서 자유텍스트에서 "매수인이 임차보증금을 떠안는가"를 2단계로 판정합니다.

**강한 신호(인수 명시 문구)** — 실측 명세서 원문에서 점진 보강해 온 목록:
```
대항력 있는 임차인 / 대항력있는 임차인 / 인수되는 경우가 발생
매수인에게 인수 / 매수인 인수 / 매수인이 인수
매수인이 부담 / 매수인에게 부담 / 매수인 부담          ← '인수' 대신 '부담' 변형(H5)
미배당 잔액은 매수인 인수 / 배당받지 못한 잔액이 매수인에게 인수
매수인에게 대항할 수 있는                               ← 대구 2025타경669 원문에서 미탐 발견 후 추가
대항력 여지 있는 / 대항력 있는 주택임차권 / 대항력 있는 임차권   ← mulBigo 실측 변형(7/22)
```

**약한 신호**: `임차권등기` — 임차권등기명령 자체가 대항력+우선변제권 유지 신호(보수적).

**인수-해소 문맥** — 이 표현이 붙은 절은 위험이 아니라 반대(인수 0원 확정/말소 예정) 신호:
```
인수하지 아니 / 인수하지 않 / 인수되지 아니 / 인수되지 않 / 인수할 권리 없
말소 동의 / 말소동의 / 말소에 동의 / 말소를 조건 / 말소 조건 / 말소조건
대항력 포기 / 대항력을 포기 / 임차권등기 말소 / 임차권등기의 말소
```

**판정 규칙(2단)**:
1. 표준 경고문 제거 → 해소 절 제거 → 남은 텍스트에 **강한 신호**가 있으면 `True`.
2. **약한 신호(임차권등기)는 문서 어디에도 해소 표현이 없을 때만** `True` — 말소동의 확약·대항력
   포기가 **다른 절**에 있는 경우가 흔해서(실측 오탐 15건), 등기 존재만으로는 위험을 주지 않음.

강한 신호는 절 단위로 살리고(혼재 명세서의 인수 절 보존 = 미탐 방지), 약한 신호는 문서 단위로
억제하는(오탐 방지) 비대칭이 이 판정기의 핵심 설계입니다.

## §3. 대항력 임차인 — 2계층: 날짜 판정 (`analyze_priority`)

문구 판정(§2)은 "법원이 인수라고 썼는가"를 읽는 것이고, 날짜 판정은 **"왜 인수인가"를 전입일 vs
말소기준일 비교로 직접 검증**합니다. 법리: *전입일 ≤ 말소기준일 → 대항력 있음(매수인 인수) /
전입일 > 말소기준일 → 대항력 없음(낙찰로 소멸)*.

**말소기준일**: `senior_lien`(최선순위 설정)의 **첫 날짜** + 근처의 유형 키워드(근저당권/근저당/저당권/
전세권/담보가등기/가압류/압류/경매개시결정/경매개시/임차권등기 — 앞선 담보물권·압류류가 말소기준).

**전입일 — 출처 우선순위**:
1. **현황조사서 확정 임차인의 실전입일**(최우선): `is_tenant_like`(보증금>0 or 확정일자 or 임차용도
   or 임차부분 — 소유자 전입과 구분하는 판정)인 세대의 전입일 중 **가장 이른 것**(min — 가장 이른
   전입 = 대항력 최강). ★호출측이 반드시 임차인만 걸러 넘겨야 함 — 소유자 전입일을 넘기면
   false-positive.
2. 없으면 명세서 자유텍스트에서 `전입(신고)?(세대|일)?자?` 라벨 뒤 날짜 스캔 — '신고' 변형 허용이
   핵심(C3): 법원 표준 라벨이 "전입신고일자"인데 종전 정규식은 '신고'가 끼면 미매치 →
   실데이터에서 날짜 판정이 사실상 무력화됐던 버그.

**verdict 6종** (각 판정에 한국어 근거 note + 등기부 확인 권고가 함께 생성됨):

| verdict | 조건 | 의미 |
|---|---|---|
| `confirmed_opposable` | 전입 ≤ 말소기준 | **대항력 있음** — 배당 부족분 매수인 인수 |
| `not_opposable` | 전입 > 말소기준 + 명세서 인수 문구 없음 | 대항력 없음 — 낙찰로 소멸 |
| `contradiction` | 전입 > 말소기준**인데** 명세서는 인수 기재 | 임차권등기명령 등 특수사유 또는 파싱오류 — 검증 대상으로 노출(숨기지 않음) |
| `dates_incomplete` | 말소기준 있음 + 인수 문구 있음 + 전입일 없음 | 법원 판정만 신뢰, 날짜 근거는 미확보 |
| `no_basis` | 판정할 날짜 없음 | 판정 불가 |
| `possible_opposable` | (no_basis에서만 승격) **관계 미상 전입세대**의 전입 ≤ 말소기준 | **대항력 '여지'** — 아래 참조 |

**`possible_opposable`이 존재하는 이유(7/23 신설)**: 현황조사서 전입세대 중 임차 신호(보증금·확정일자·
용도)가 안 잡히는 세대(`is_tenant_like=False`)를 종전엔 소유자로 단정해 무시 → 부산 2022타경3289
삼환아파트에서 전입 1996 ≤ 말소기준 2002인 세대를 못 잡는 false-negative(유료 경매사이트는 '대항력
있음' 표기). 법원 원문 자체가 "소유자와의 관계를 **알 수 없는** ○○ 세대가 전입"이므로 소유자 단정은
근거가 없음 → 관계 미상 전입이 말소기준보다 앞서면 **'있음'(확정)보다 약하고 '없음'(clean)보다 강한
경고**로 승격. 단 이미 확정/모순/미완 판정이 선 경우는 존중(no_basis일 때만 승격 = 과잉경보 가드).
확정 임차인 전입일(`tenant_moveins`)과 관계 미상 전입일(`ambiguous_moveins`)을 **분리해서** 넘기는
것이 이 설계의 규약입니다.

## §4. 인수금액 (`detect_assumed_amount`) — 줄 단위 스캔 + 5단 필터

매수인이 낙찰가 **외에 추가로 떠안는 금액**(원). 명세서 자유텍스트를 줄(line) 단위로 스캔하며,
각 줄을 다음 순서의 필터에 통과시킵니다 — **이 순서 자체가 판정 로직**입니다:

```
줄마다:
 1. 인수 문맥 키워드("인수"·"미배당"·"떠안"·"부담") 없으면 → 무시
 2. 직접 부정("인수하지 아니/않/되지 아니/되지 않" 6종) 있으면 → 인수 0원 확정, 제외  ★최우선
 3. 이중부정("말소되지 않/아니"·"소멸되지 않/아니"·"변제되지 아니/않") 있으면
      → 일반 부정 검사를 건너뜀   ("말소되지 않고 … 매수인이 인수함"은 '말소'가 있어도 인수다)
    이중부정이 없고 일반 부정("없"·"말소"·"소멸") 있으면 → 제외
 4. 재고지 마커("재안내"·"재고지"·"재통지"·"상기"·"앞서"·"위 보증"·"위 임차"·"위 임대차"·
    "참고로"·"다시 안내") 있으면 → 제외   (앞 임차인 금액의 반복이지 새 인수액이 아님)
 5. 공백 제거 후 완전 동일한 줄은 1회만   (명세서 요지 ↔ 비고 복붙 이중계산 방지)
 → 통과한 줄의 금액을 합산(total)
```

2→3의 순서가 중요합니다: "…변제되지 아니한 보증금은 매수인이 **인수하지 아니함**(특별매각조건)"은
이중부정('변제되지 아니')이 있어도 직접 부정이 이기고 인수 0원입니다(#15).

**한 줄 안의 금액 계산(`_line_assumed`)**:
- **잔액 규칙 우선**: "금 X원 **중 미반환/배당받지 못한/잔액** Y원" 패턴이면 원계약 보증금 X가 아니라
  **실제 인수액 Y**를 채택(#16).
- 그 외: 한 줄에 임차권/전세권/보증금 언급이 **2건 이상**이면 서로 다른 금액의 **distinct 합산**
  (다건 과소표시 방지, 같은 금액 반복표기는 set으로 이중계산 차단), 1건이면 max.

**줄 사이는 합산**(H1, 7/22): 같은 보증금이 서로 다른 임차인 줄에서 나오면 **합산**합니다 — 종전의
전역 set-dedup은 '같은 보증금 임차인 2명'을 1명치로 과소산정하는 위험한 미탐이었음. "같은 금액 2명"
(합산해야 함)과 "한 임차인 금액 재안내"(1회여야 함)는 텍스트만으론 금액이 같아 구분 불가 → 그래서
4번 재고지 마커와 5번 동일 줄 dedup이 존재합니다. 임차인 전입일 실데이터가 있으면 그쪽(§5의 구조화
합산)이 우선입니다.

**금액 파서(`_korean_won`)**: 순수 숫자("150,000,000원")와 한글 단위 혼합("1억9천5백만원", "천5백만원",
"금5,000만원") 모두 원 단위 정수로 환산. 억=×1e8, 만 단위 계수는 천/백/십 혼합표기(_mixed_man)까지 처리.

## §5. 인수금액 미상일 때 — 2중 보수 폴백

1. **보증금 폴백(`detect_deposit_amount`, #9)**: 인수 부담(burden)은 확실한데 인수액을 못 읽었으면
   (`amount_unknown` — UI에 "+α"로 표기) 명세서 원문의 `보증금 X원` 표기를 부정절 제거 후 수집해
   **보수 추정치로 채택** — 임차권 미소멸 물건이 무차감으로 랭킹 상위를 점하지 않게 함.
2. **현황조사서 기반 보정(`opposable_deposit`)**: 날짜 판정이 `confirmed_opposable`이면, 말소기준일
   이전(≤)에 전입한 **is_tenant_like 임차인들의 보증금 합**을 계산해 서빙 시점에
   `인수액 = max(문구 파싱값, 보증금 합)`으로 상향 보정(web.py) — 구조화 데이터가 자유텍스트 파싱보다
   우선한다는 원칙.

이렇게 확정된 `assumed_amount`는 ①실질취득원가에 가산(가격갭 하락) ②보수 차익
`profit_low = 검증하한가 − 비용 − assumed_amount`에서 직접 차감 ③하드게이트 비율 판정(§6)에 사용
— 세 곳 모두에 반영됩니다.

3. **그래도 금액을 못 읽으면 — 추천 자체를 금지**(`burden_amount_unknown`, 2026-07-23 감사 P-01):
   위 두 폴백으로도 금액이 안 나오면 `assumed_amount = 0`이 되는데, 종전엔 이 0이 **'부담 없음'과
   구분되지 않아** 인수 명시 물건이 '차익 유력·양호·관심'으로 추천됐습니다(감사 실측 — 추천 573건 중
   248건이 이 상태). 차감할 금액을 모르면 보수 차익 자체가 과대평가된 값이므로,
   `derive_grade`가 추천계열 등급을 **'주의'로 상한**합니다(채점·서빙 폴백 동일 적용).
   `/api/listings`는 `assumed_amount_unknown: true`를, CSV는 `인수부담="있음(금액 미상)"`·
   `유효차익=공란`을 내보냅니다 — **모름을 0으로 계산하지 않는다**는 원칙(§7)의 금액 버전입니다.
   ※ 알려진 정밀도 한계: 비고란에 "대항력은 포기하며"·"말소동의" 확약이 있는 물건도 현재는 부담으로
   남아 함께 강등됩니다(실측 58건). 확약의 효력 판단은 별도 과제입니다.

## §6. 특수권리·점유 판정과 스코어 반영

**특수권리(`detect_special_rights`)** — 표준 라벨 9종 사전(표기 변형 매핑): 유치권 / 법정지상권 /
지분(+"N분의 M" 정규식 — '부분의' 오탐 분리) / 분묘기지권 / 대지권미등기 / 위반건축물 / 가등기 /
가처분 / 토지별도등기(뒤 3종은 감사에서 clean 오판 발견 후 추가 — 실DB 가등기24·가처분10·별도등기
39건이 안 잡히고 있었음). **부존재 절 제외**: "유치권 신고 없음"·"성립 여지 없음" 같은 부존재 명시
표현(19종)이 **같은 절**에 있으면 검출 제외 — 종전엔 키워드 출현만으로 유치권(fatal)→하드게이트
'위험' 직행해 정상 물건을 영구 배제(C2). 지분매각은 별도 정규식 `지분\s*(매각|경매)`로 법원 분류어만
잡음('N분의M' 단순 언급 오배제 방지, 실측 376건).

**점유유형(`detect_occupant_type`)**: 다수점유 > 임차인 > 소유자점유 > 공실 우선순위(임차인·소유자
혼재 시 인수 위험 큰 임차인 채택). **정보가 없으면 '소유자점유'**(명도비용 큰 쪽) — 보수 기본값.

**종합 배지(`summarize` → `RightsBadge`)** — 목록 랭킹과 상세 페이지가 **같은 함수**를 쓰므로 사실이
갈릴 수 없음:
```
burden = 대항력(§2) or 인수액>0(§4·5) or 특수권리 or unresolved_text or 선순위전세권
```
- `unresolved_text`: **부정절 제거 후에도** surviving_rights/lien_note에 실질 텍스트가 남는가 —
  원문 존재만으로 burden 처리하면 "임차권등기(다만 말소동의 확약서 제출됨)" 같은 소멸 예정 권리가
  오판돼 실제 clean 물건 86건이 추천에서 빠졌던 것(M1)의 수정.
- `선순위전세권`: 최선순위 설정이 전세권이면 배당요구 여부에 따라 인수가 갈리는 특수사례 → burden(#14).

**스코어 반영(`score.py`)**:
```
권리점수 = 100 − (인수액/최저가)×100 − Σ특수권리 페널티(종류당 1회) − 대항력 30 − 점유 페널티
특수권리 페널티: 유치권30 · 지분매각30 · 법정지상권25 · 가등기25 · 가처분25 · 지분20 · 분묘기지권20
                대지권미등기15 · 위반건축물15 · 토지별도등기15 · 선순위전세권20 · 기타 10
점유 페널티:    공실0 · 임차인10 · 소유자점유15 · 다수점유25 · 미상 15

하드게이트(is_hard_gated): 인수액/최저가 > 0.30  또는  치명 특수권리(유치권·지분매각)
  → 권리점수 0 + 최종 스코어 상한 25 = '위험' 등급 강등
  (권리점수만 0으로 만들면 갭 가중치 50% 때문에 유치권 물건이 상위 노출되던 허점의 봉쇄.
   최저가 0원이면 비율을 1.0으로 간주 = 게이트 — 0 나눗셈을 안전 쪽으로 처리)
```
상세 페이지는 게이트 발동 시 **사유를 그대로 노출**합니다("인수금액 비율 43% (>30%)", "유치권 신고").

## §7. "모름"과 "없음"의 구분 — 3중 가드

보수 원칙의 다른 반쪽: 근거가 없는데 "없음(clean)"이라고 말하는 것도 침묵실패입니다.

1. **`is_empty`** — 작성일·말소기준·인수권리·유치권란 전부 빈 요지는 판정 근거 자체가 없음 →
   **저장하지 않고** 배지도 안 만듦 = '권리미확인' 유지(빈 pgj15B 응답이 "낙찰 후 추가 인수 없음"
   초록으로 표시되던 버그의 수정).
2. **`opposability_assessable`** — 자유기술란 3칸(surviving_rights/lien_note/remark)이 전부 비면
   (실DB의 19%!) 대항력은 '없음'이 아니라 **'모름'**: 말소기준·작성일만 있으면 is_empty=False라서
   rights_verified=True → "대항력 임차인 발견 안 됨" 초록이 나가던 false-negative(삼환 실사례)의
   수정. 이 경우 배지·판정은 미생성하되 참고정보(말소기준·기일·감정요항)는 표시.
3. **미크롤 물건** — badge 자체가 None = UI '권리 미확인' + 등급 `권리미확인`(하드게이트가 아직
   작동할 수 없는 상태임을 명시).

즉 물건의 권리 상태는 반드시 넷 중 하나입니다: **미확인**(크롤 전/근거 없음) / **깨끗**(명세서 확인
결과 신호 없음) / **부담**(금액 확정 또는 +α) / **위험**(하드게이트). "깨끗"은 언제나 "명세서를 실제로
읽고 신호가 없었다"는 뜻이지 "정보가 없다"는 뜻이 아닙니다.

## §8. 알려진 한계 (문서화된 정직성)

- **현황조사서는 기본 OFF**(물건당 +1콜 예산 문제) — 전입일 실데이터 커버리지가 제한적이라 대부분
  물건은 문구 판정(§2)+`dates_incomplete`에 머뭅니다. 소량 검증만 완료, 대량 크롤은 대기(B-2).
- 목록 비고(mulBigo)에 "대항력" 문구가 있는 1,583건 중 상세 미크롤분의 활용은 후속 과제.
- **등기부등본은 보지 않습니다** — 법원 명세서·현황조사서가 원천이며, 모든 판정 note에 "등기부
  확인 요망"이 붙는 이유. 이 엔진은 1차 필터이지 권리분석 대체가 아닙니다(면책 참조).
- 텍스트 규칙의 본질적 한계: 법원 서기의 자유 서술 변형은 무한하므로, 미탐 발견 시마다 목록을
  보강하고(주석에 사례 물건번호 기록) 회귀 테스트로 고정하는 **점진 보강 모델**입니다.

## 매칭 → 시세추정 (`matcher.py`)

크롤한 경매물건과 실거래를 이어 붙이는 계층 매칭입니다. **비교군이 틀리면 통계가 아무리 좋아도 결과가
틀리므로**, 어느 집합에서 나온 시세인지(`scope`)를 신뢰 등급의 근거로 함께 반환합니다.

```
0) 네이버 complexNo 확정 comps (estimate_from_complex_trades — 이름매칭 우회, 최우선)
1) 같은 단지 + 같은 평형(±3%)   → same_complex_same_area  (추천 인정)
2) 같은 단지 + 인접 평형(±10%)  → same_complex_near_area  (참고치)
3) 같은 법정동 + 같은 유형·면적 → same_dong_fallback      (참고치 — 추천 금지)
추정시세 = (최근성 필터 → 이상치 트림 → 평단가 중앙값) × 전용면적
```

- **유형 분리**: 아파트를 아파트 실거래로만, 오피를 오피로만(혼입 차단). 시세추정은 **아파트·
  오피스텔만** — 빌라·단독·상가·토지는 "시세추정불가"로 분리(거짓 차익 방지).
- **감정가 교차검증**: 추정시세가 감정가의 2.5배(폴백 1.5배) 초과 또는 0.6배 미만이면 비교군 오류
  신호로 시세를 **말하지 않음**. 확정단지 경로에도 감정가 하한(0.35배) 게이트(네이버 오매칭 시 est
  붕괴 차단). 감정가 괴리로 확정 comps가 기각되면 이름매칭 폴백도 금지(적신호 유지).
- **표본 게이트**: 실기반 표본 3건 미만이면 밴드 생성 금지, 5건 미만이면 추천 제외.
- **2선 밴드**: 검증 하한가(보수)~기준가(중앙값) 두 선 제시(단일가 과신 방지). 창 확장(24/60개월)
  사용 시 신뢰 하향 배수 적용(옛 거래로 표본 부풀려 등급이 올라가는 것 상쇄).

## 차익 스코어 (`score.py`)

```
score = ( 가격갭 × 0.50 + 권리 × 0.30 + 환금성 × 0.20 ) × 신뢰계수(0.6~1.0)
실질취득원가 = 최저입찰가 + 취득세 + 명도비 + 수리비 + 인수금액
가격갭       = (추정시세 − 실질취득원가) / 추정시세
```

| 하위점수 | 가중치 | 데이터 소스 |
|---|---|---|
| 가격갭 | 50% | 법원경매 최저가 + 국토부/네이버 시세 + 세율 룰 |
| 권리 깨끗함 | 30% | 매각물건명세서·현황조사서(courtauction 상세 크롤) |
| 환금성 | 20% | 실거래량 + 물건종류·지역유동성 |
| 신뢰계수 | ×0.6~1.0 | 실거래 매칭 표본수(3↑=1.0 / 2=0.85 / 1=0.7 / 0=시세추정불가) |

**하드게이트**: 인수금액/최저가 > 30% 또는 치명 특수권리(유치권·지분매각)면 최종 스코어 상한 25로
**"위험" 강등**. 비고의 채권자 매수신청액은 `유효 최저가 = max(공고가, 매수신청액)`으로 반영.

**등급**: `차익 유력`(80+) · `양호`(60~79) · `관심`(40~59) · `주의`(<40) · `위험`(하드게이트) ·
`차익없음`(보수차익≤0) · `시세추정불가`(표본 부족) · `미지원유형`(아파트·오피 외) · `권리미확인`.
권리 요지가 빈 물건은 '깨끗'이 아니라 **'권리미확인'**(빈 값 ≠ 없음 — 보수 원칙).

## 재매각 경고 (`resale_history`) — 낙찰됐다가 되돌아온 물건

물건상세의 기일 이력(`gdsDspslDxdyLst` → `listing_rights.schedule`)에서 **결과가 '매각'인 회차 뒤에
더 늦은 기일이 있으면** 그 물건은 낙찰됐다가 되돌아온 것이다. 통계가 아니라 **그 물건 자체의 확정
사실**이라 표본 게이트 없이 그대로 표시한다. 이력이 없으면 아무것도 그리지 않는다.

**실측(2026-07-23, 권리크롤 14,430건)**

| 항목 | 값 |
|---|---|
| 재매각 물건 | **558건 (3.9%)** — 대금 미납 463 · 매각 불허가 74 · 매각허가 취소 21 |
| 2회 이상 반복 | 39건 (최대 5회) |
| 평균 저감률 | **63.8%** (일반 36.8%) — 가격이 반토막 나 갭 점수가 구조적으로 높게 나온다 |
| 평균 유찰 | **4.53회** (일반 1.99회) |
| 추천계열에 노출 중 | 차익 유력 6 · 양호 7 · 관심 17 = **30건** |

즉 재매각 물건은 **싸 보여서 추천 상위로 올라오는 편향**이 있다. 배지가 그 함정을 드러낸다.

- 판정 단위는 **물건**(court, case_no, item_no) — `schedule` 이 물건별로 다르다(실측: 부산 2024타경62594는
  물건 57개에 이력 21종). 사건 단위로 뭉치면 다른 물건 이력이 섞인다.
- **낙찰가는 표시하지 않는다.** 대법원 응답의 `dspslAmt`(매각금액)는 스키마에만 있고 값이 항상 비어 온다
  (실측: 매각 회차 15/15 null). 배너가 보여주는 금액은 **그 회차 최저입찰가**이며 라벨에 명시한다.
- 스코어·등급에는 **반영하지 않는다**(표시 전용). 감점 정책은 별도 결정 사항.

## 입찰가 시뮬레이터 (`bidsim.py`) — 표면차익 → 실현 손익

목록·스코어의 '예상 차익'은 **취득 시점 표면차익**이다(최저입찰가 + 취득세만 반영). 명도비·대출이자·
양도세는 "매도가·보유기간 가정이 필요해 주관이 개입된다"는 이유로 빠져 있었다. 시뮬레이터는 그 가정을
**사용자가 직접 입력**하게 만들어 벽을 넘는다. 근거·세율은 `docs/tax-auction-knowledge.md` **§5**가 단일 출처.

```
총투입   = 입찰가 + 취득세(입찰가 기준 재계산) + 인지세 + 법무·채권 + 인수금 + 명도 + 수리 + 미납관리비
실투자금 = 총투입 − 대출(입찰가 × LTV, 상한 80%)
세후순익 = 매도가 − 총투입 − 대출이자 − 매도중개보수 − (양도세 + 지방소득세)
★손익분기 입찰가 = 세후순익 = 0 이 되는 입찰가 (순익은 입찰가에 단조감소 → 이분탐색)
```

- **손익분기 입찰가**가 결론이다. "차익 3억"이 아니라 "**여기까지 써도 남는다**"가 입찰표에 쓰는 숫자.
- 취득세는 목록과 달리 **입력 입찰가로 재계산**된다(낙찰가가 오르면 세율 구간도 오른다).
- 양도세: 단기 1년↓ 70%/60%(주택)·50%/40%(비주택), 2년↑ 기본세율 누진 + 장특공(3년↑ 연 2%, 최대 30%).
- **보수 처리**(과대 수익 추정 방지): 명도·수리·미납·이자는 필요경비 **미공제**, 1세대1주택 비과세·장특공
  표2(최대 80%) **미적용**, 중개보수는 **상한요율**, 오피스텔은 취득세만 비주택(4.6%)이고 양도세 단기세율은
  주택(70/60%)으로 간주.
- **상세페이지 전용** — 목록·스코어·등급에는 일절 영향을 주지 않는다(표면차익 정의 유지 = 회귀 차단).
- 계산은 전부 서버(`/api/bidsim`, DB 무접근 순수 계산). JS에 세율을 복제하지 않아 단일 출처가 유지되고,
  JS가 꺼져 있어도 서버 렌더 초기값이 남는다.

## 서빙 (Flask + Supabase 미러)

- 수집·채점 결과는 로컬 `auction.db`(SQLite, WAL) 저장 후 **Supabase**(`auction_scored_listings` 등)로
  적재(`store_rest.py`, REST/service key — Vercel/GitHub Actions 친화). 웹은 Supabase만 읽습니다.
- 서빙 시점에 국토부가 없는 물건은 `market_view`로 **KB→호가→전세 폴백**을 라이브 적용.
- 식별자는 전 계층 **`(court, case_no, item_no)` 복합 PK**(사건번호는 법원별 독립 채번).

| 경로 | 설명 |
|---|---|
| `/` | 차익순 목록(갭미터·경고뱃지·필터 폼·사건번호 검색) |
| `/property/<사건번호>` | 물건 상세 — 시세근거·권리 안전성·대항력 판정·환금성·사진·실거래 차트·지도·입찰가 시뮬레이터 |
| `/api/bidsim?bid=&sell=&months=&ltv=&rate=&type=&area=` | 입찰가 시뮬레이터 계산(순수 함수, DB 무접근) |
| `/methodology` | 차익 스코어 공식·가중치·캘리브레이션 공개(투명성) |
| `/api/listings?min_score=80&type=아파트&region=서울&sort=profit` | JSON API |

## 미래 유지보수자를 위한 함정 목록

1. **네이버 API는 만원 단위** — 원 단위 값은 200+error 바디로 침묵 실패한다(실측 사고 이력).
2. **현황조사서는 같은 세션에서 상세 선행 필수** — 단독 호출은 200 + `{ipcheck:false}` 빈 응답.
3. **취소거래 판정값은 `'O'`**(국토부 cdealType, 네이버 deleteYn 모두) — 'Y'가 아니다.
4. `budget_file` 영속은 **crawl_rights만** 켠다 — 목록 크롤 예산은 동적 산출·비영속(코드 주석과 다름).
5. `--max-pages` CLI 기본 25 vs 파이프라인 함수 기본 10 — 직접 함수 호출 시 기본값이 다르다.
6. 캐시 키 형식을 바꾸면 직후 1회는 diff가 전량 '신규'로 보인다.
7. 빈 테이블은 data_gates를 **위반 0건으로 통과**한다 — '수집 0건 보존' 장치가 별도로 있는 이유.
8. PII 제외어 판정은 **정확일치만** — 접두일치로 바꾸면 실명("전원철")이 마스킹을 빠져나간다.
9. H4 카나리는 **키 존재** 판정(값 null은 정상)이고 핵심 3키 **전부** 있어야 정상 — any()로 되돌리면
   침묵실패 구멍이 다시 열린다.
10. 새 엔드포인트는 추측으로 파서를 만들지 말 것 — `probe_detail.py`처럼 라이브 1콜로 정찰 먼저.
11. 인수금액 판정의 부정 검사 순서는 **직접부정 → 이중부정 → 일반부정**이다 — 순서를 바꾸면
    "말소되지 않고 인수함"(인수임)과 "인수하지 아니함"(인수 아님)을 서로 반대로 오판한다.
12. 해소·부존재 판정은 **절 단위**(구분자에 콤마 포함)다 — 문서 전체 단위로 바꾸면 다중임차인 혼재
    명세서("A는 말소동의, B는 인수")에서 진짜 인수 신호를 삼킨다. 반대로 약한 신호(임차권등기)만은
    문서 단위 억제가 맞다(§2의 비대칭 설계).
